# TCPFighter

클라이언트 접속부터 이동·전투 동기화까지 처리하는 2D 액션 MMO 서버입니다.
select 멀티플렉싱으로 구현했고, 15,000 세션을 목표로 잡았습니다.

- **2만 세션 접속** — 학원 환경, 더미 클라이언트 기준
- **625개 섹터 AOI** — 주변 9칸에만 브로드캐스트해 전송량 절감
- **서버 권위 좌표 검증** — 클라이언트의 위치 조작 차단
- **부하 테스트** — 세션이 늘 때 Loop/sec 125,539 → 8,142
- **크래시 해결** — 순회 중 세션 삭제로 인한 반복자 무효화, 예약 정리 구조로 수정

> 이 저장소에는 서버 코드만 있습니다.
> 클라이언트와 더미 클라이언트는 학원에서 제공한 것이라 따로 코드가 없습니다.

`C++` `Winsock2` `select` `섹터 기반 AOI`

---

## 구조

싱글 스레드 select 모델입니다. 한 루프에서 소켓 이벤트를 받고 컨텐츠까지 처리합니다.

브로드캐스트는 섹터 단위로 처리하여, 맵을 625개 섹터로 나누고
이벤트가 생기면 자신이 속한 섹터와 인접한 8개 섹터, 총 9개 섹터에만 전송합니다.

캐릭터가 섹터 경계를 넘으면 이전 섹터에서 제거하고 새 섹터에 등록합니다.
이때 시야에서 빠진 쪽에는 삭제 패킷을, 새로 들어온 쪽에는 생성 패킷을 보냅니다.

```
      +-----+-----+-----+-----+-----+
      |     |     |     |     |     |
      +-----+-----+-----+-----+-----+
      |     |  *  |  *  |  *  |     |
      +-----+-----+-----+-----+-----+
      |     |  *  |  X  |  *  |     |
      +-----+-----+-----+-----+-----+
      |     |  *  |  *  |  *  |     |
      +-----+-----+-----+-----+-----+
      |     |     |     |     |     |
      +-----+-----+-----+-----+-----+

      X   이동한 플레이어
      *   패킷을 받는 섹터
      빈칸  전송하지 않음
```

위 그림과 같이 이동한 플레이어를 기준으로 9개 섹터에만 전송됩니다.

서버가 애초에 보내지 않은 좌표는 클라이언트 메모리에 존재하지 않으므로,
클라가 메모리를 확인하여 시야 밖 다른 캐릭터의 좌표를 읽어내는 방식은 성립하지 않습니다.

좌표는 서버에서 검증하여, 직전 위치와의 거리와 경과 시간, 이동 속도를 비교해
불가능한 이동은 폐기합니다.

## 크래시 해결

끊긴 세션을 정리하는 과정에서 크래시가 발생했습니다.
세션 목록을 순회하면서 같은 목록에서 즉시 삭제하는 구조라
반복자가 무효화된 것이 원인이었습니다.

삭제 대상을 예약 목록에 모아두고,
해당 프레임의 순회가 끝난 뒤 일괄 정리하도록 변경했습니다.

## 부하 테스트

세션 수를 늘려가며 성능을 측정했습니다.

지표로는 초당 게임 루프 회전 수를 사용했습니다.
루프 회전 수가 곧 서버가 처리할 수 있는 프레임 수이므로,
이 값이 떨어지면 처리량이 부족하다는 의미입니다.

CPU 사용률은 지표에서 제외했습니다.
게임 루프가 busy-spin 구조라 대기 중에도 CPU를 점유하기 때문에
부하와 무관하게 항상 높게 측정됩니다.

유휴 상태에서 125,539였던 Loop/sec이 세션 1,540 시점에 8,142까지 떨어졌습니다.
아래는 그 시점의 더미 클라이언트 출력입니다.

```
Connect Try : 6430 / Error : 25
Disconnect from Server : 718
-----------------------------------
Session Count : 1540
Character Count : 1538
-----------------------------------
Sync Message Count : 542970
Contents Error : 0
Packet Message Error : 0
RTT : Avr 866ms / max 866ms
```

동기화 메시지 54만 건을 주고받는 동안 컨텐츠 오류와 패킷 오류는 0건입니다.
다만 왕복 지연이 866ms까지 올라갔고, Loop/sec은 유휴 대비 15분의 1로 떨어졌습니다.
원인은 세 가지였습니다.

**첫째, fd_set 등록 비용**
Windows의 `fd_set`은 소켓 배열입니다. `FD_SET` 매크로는 소켓을 넣을 때마다
이미 있는지 확인하려고 배열을 처음부터 훑습니다.
n개를 등록하면 훑는 횟수가 `n(n-1)/2`가 됩니다.

**둘째, 매 프레임 전체 재검사**
select는 매 프레임 전체 소켓을 다시 검사합니다.
이벤트가 없는 소켓까지 확인하므로 프레임당 검사 횟수가 5,021회까지 올라갔습니다.

**셋째, FD_SETSIZE**
기본 상한이 1024입니다. Windows에서는 재정의로 늘릴 수 있지만,
늘려도 위의 훑는 비용은 그대로 남습니다.

## 결론

select의 폴링 비용은 소켓 수에 비례합니다.
소켓이 수십에서 수백 개 수준이면 이 비용이 문제가 되지 않고,
구조가 단순해 유지하기 쉽다는 이점이 남습니다.
서버 간 통신, 관리·모니터링 서버, 개발용 툴이 여기에 해당합니다.
부하 테스트 클라이언트도 select로 충분했습니다.

반면 클라이언트 접속을 직접 받아 수천 명을 한 프로세스가 감당하는 자리라면
전체를 훑지 않고 완료된 것만 통보받는 구조가 필요합니다.

다음 프로젝트를 [IOCP 채팅 서버](https://github.com/yjj2123/iocp-chatserver)로 잡은 이유입니다.
